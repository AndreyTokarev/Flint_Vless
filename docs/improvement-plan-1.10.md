## Группа I. Сначала то, что влияет на обход блокировок

### I.1. Обновить Xray в комплекте и в запасном пути (находка 1)

**Зачем.** Стоящий 1.8.7 (август 2024) и закреплённый `XRAY_VERSION=v1.8.24` старше исправления v25.6.8 (08.06.2025), после которого REALITY имитирует post-handshake records и перестаёт отличаться активным зондированием. Пока версия старая, качество маскировки не зависит от качества нашего кода.

**Что делать.**

1. Поднять версию по умолчанию в [kit/install.sh](../kit/install.sh) и [config/flint.env.example](../config/flint.env.example).
2. Хранить в комплекте контрольную сумму архива, как это уже сделано для Telegram-прокси: версия закреплена, подмена файла не установится.
3. Добавить в `install.sh` печать версии Xray в итоговую сводку (сейчас печатается `xray version | head -n1`, но не сравнивается с ожидаемой).
4. В README прямо написать: **обновлять нужно обе стороны** — если сервер провайдера старше v25.6.8, роутер это не исправит.

**Эскиз.** В `kit/install.sh`:

```sh
XRAY_VERSION="${XRAY_VERSION:-v26.9.9}"
XRAY_SHA256_ARM64="<sha256 архива Xray-linux-arm64-v8a.zip для этой версии>"
...
if [ ! -f /usr/bin/xray ]; then
	curl -fL -m 600 -o /tmp/xray.zip \
		"https://github.com/XTLS/Xray-core/releases/download/$XRAY_VERSION/Xray-linux-arm64-v8a.zip" || true
	if [ "$(sha256sum /tmp/xray.zip 2>/dev/null | cut -d' ' -f1)" = "$XRAY_SHA256_ARM64" ]; then
		unzip -o -q /tmp/xray.zip xray -d /usr/bin
	else
		say "xray: архив не скачался или сумма не совпала, остаётся текущий бинарник"
	fi
	rm -f /tmp/xray.zip
fi
```

Проверка версии на роутере после установки:

```sh
say "xray: $(xray version | head -n1)"
case "$(xray version | head -n1)" in
	*"1.8."*) echo "NOTE: Xray старше 25.6.8: REALITY отличим активным зондированием, обновите сервер и роутер" ;;
esac
```

**Проверка.** `tests/run.ps1` (сценарий `redeploy` проверяет итог установки), вручную — `xray version` на роутере, `flint-node apply` после обновления, проверка выхода: `curl -x http://127.0.0.1:1087 https://ifconfig.me`.

**Трудозатраты:** средние (нужно получить и закрепить сумму, проверить совместимость конфига-шаблона с 26.x). **Риск:** средний — в 26.x могли измениться параметры конфигурации; поэтому обязателен `xray run -test` перед применением (в проекте он уже есть в `flint-node render`). **Выигрыш:** маскировка перестаёт быть заведомо отличимой; открывается XHTTP, FinalMask, ECH, PQ-обмен (см. исследование).

### I.2. Режим «DNS через туннель» и честные подсказки в панели (находка 2)

**Зачем.** Сейчас при блокировке DoH по SNI пользователь перебирает Cloudflare → Google → Quad9 → AdGuard и не понимает, почему не помогает. Надёжен только резолвинг внутри туннеля (запрос уходит в Xray и дальше на сервер).

**Что делать.**

1. Добавить в [flint-dns](../kit/files/usr/bin/flint-dns) четвёртый режим `tunnel`: dnsmasq направляет запросы не на `127.0.0.1:5053`, а на локальный DNS-вход Xray, который ходит на резолвер через туннель.
2. В шаблоне Xray ([kit/files/etc/xray/template.json](../kit/files/etc/xray/template.json)) добавить вход `dns-in` — `dokodemo-door` на `127.0.0.1:5353` с адресом назначения `1.1.1.1:53`. Тогда запросы попадают в существующие правила маршрутизации: DNS-серверы провайдера уходят напрямую только если это прописано, остальное — через VLESS.
3. В панели на вкладке DNS: подсказка «если DoH перестал отвечать, дело может быть в блокировке по имени резолвера; смена сервера внутри DoH не поможет — используйте DNSCrypt или DNS через туннель».
4. В README — раздел «Что делать, если перестал работать защищённый DNS».

**Эскиз.** В `template.json`:

```json
{
  "tag": "dns-in", "listen": "127.0.0.1", "port": 5353,
  "protocol": "dokodemo-door",
  "settings": { "address": "1.1.1.1", "port": 53, "network": "tcp,udp" },
  "sniffing": { "enabled": false }
}
```

В `flint-dns` добавить режим и upstream:

```sh
# upstream(): режим tunnel — резолвер внутри туннеля
if [ "$1" = tunnel ]; then echo "1 127.0.0.1#5353"; return; fi
```

и в `mode()`:

```sh
mode() { case "$(cat "$MODE_F" 2>/dev/null)" in udp) echo udp ;; dnscrypt) echo dnscrypt ;; tunnel) echo tunnel ;; *) echo doh ;; esac; }
```

**Проверка.** Новый сценарий `tests/router/dns.sh`: переключить режим на `tunnel`, проверить `nslookup example.com 127.0.0.1` и что запрос действительно идёт через туннель (`logread -e xray` или временное правило-счётчик в цепочке). Плюс проверка локальных имён (`nas01`) и совместимости с AdGuard Home.

**Трудозатраты:** средние–высокие. **Риск:** высокий — легко получить петлю (Xray спрашивает DNS у dnsmasq, dnsmasq у Xray) и сломать локальные имена; нужен явный обход `127.0.0.1` и `br-lan` в правилах Xray. **Выигрыш:** единственный режим, устойчивый к блокировке DNS по SNI.

### II.4. Один манифест состояния с колонками «бэкап / экспорт / ни то, ни другое» (находки 4, 9, 10)

**Зачем.** Сегодня три перечня (`kit/state-files`, `ENTRIES` в `flint-settings`, жёсткий список путей в `backup.ps1`/`backup.sh`) и ни одной проверки согласованности. Новый файл состояния легко добавить в один список и забыть в другом — и настройка молча не переживёт восстановление.

**Что делать.**

1. Расширить [kit/state-files](../kit/state-files) до таблицы с колонками: `имя`, `бэкап` (да/нет), `экспорт настроек` (да/нет), `комментарий`. Обратная совместимость: строки без колонок считаются «бэкап = да, экспорт = да».
2. `install.sh` читает первую колонку (как сейчас), `flint-settings` — строки, где колонка экспорта равна `да`.
3. Добавить в `tests/router/` проверку: каждый файл, который `flint-dns`/`flint-node`/`flint-tg` создаёт в `/etc/xray`, присутствует в манифесте.

**Эскиз манифеста.**

```
# имя                    бэкап  экспорт  комментарий
flint.env                да     нет      PIN и сеть: не переносим на другой роутер
nodes.conf               да     да       серверы, заданные вручную
nodes.d                  да     да       серверы подписок, файл на подписку
tgproxy                  да     да       настройки прокси Telegram и секрет
current-node             да     да       выбранный сервер
dns-hosts                да     да       локальные имена
```

Чтение в скриптах:

```sh
# state_names <backup|export>: имена файлов состояния для нужного случая
state_names() {
	awk -v want="$1" '$1 !~ /^#/ && NF {
		col = ($1 == "flint.env" && $2 == "да" && $3 == "нет") ? 3 : 3
		if (NF < 3) { if (want == "backup" || want == "export") print $1; next }
		if ((want == "backup" && $2 == "да") || (want == "export" && $3 == "да")) print $1
	}' /usr/share/flint/state-files
}
```

(Эскиз намеренно простой: главное — одно место правды и явные колонки.)

**Проверка.** Сценарий `state.sh`: добавить тестовый файл в `/etc/xray` и убедиться, что проверка полноты его ловит; прогнать `flint-settings export` и `backup` — состав совпадает с манифестом.

**Трудозатраты:** средние. **Риск:** низкий (обратная совместимость по числу колонок). **Выигрыш:** закрывается целый класс ошибок «настройка не пережила восстановление».

### II.5. Блокировка обновления по живому процессу, а не по времени (находка 5)

**Зачем.** Сейчас `find -mmin +10` удаляет каталог-блокировку у процесса, который честно работает дольше 10 минут; дальше два процесса пишут серверы одновременно.

**Что делать.** Класть внутрь блокировки PID и стартовое время, а «протухшей» считать только ту, чей процесс мёртв:

```sh
# lock: каталог с PID внутри; чужой живой процесс — отказ, мёртвый — снимаем
lock() {
	if mkdir /tmp/flint-sub.lock 2>/dev/null; then
		echo $$ > /tmp/flint-sub.lock/pid
	else
		old="$(cat /tmp/flint-sub.lock/pid 2>/dev/null)"
		if [ -n "$old" ] && kill -0 "$old" 2>/dev/null; then
			fail "$(t "Обновление уже идёт" "An update is already running")"
		fi
		# процесс умер, не убрав за собой: снимаем и пробуем снова
		rm -rf /tmp/flint-sub.lock
		mkdir /tmp/flint-sub.lock 2>/dev/null || fail "$(t "Не удалось создать блокировку" "Cannot create the lock")"
		echo $$ > /tmp/flint-sub.lock/pid
	fi
	rm -rf "$TMP"; mkdir -p "$TMP"
	trap 'rm -rf /tmp/flint-sub.lock "$TMP"' EXIT
}
```

То же для [flint-watchdog](../kit/files/usr/bin/flint-watchdog) (там блокировка своя, `mkdir "$LOCK"`), вынести в `lib.sh`, чтобы правило было одно.

**Проверка.** Сценарий: запустить `flint-sub-update` в фоне, во время него запустить второй — должен отказаться; убить первый `kill -9` (каталог остаётся) — второй должен подняться.

**Трудозатраты:** низкие. **Риск:** низкий. **Выигрыш:** невозможно одновременное обновление подписок с двух сторон (панель + крон + сторож).

### II.6. Справка команд — из блока `# Usage:` во всех командах (находка 6)

**Зачем.** Жёсткие номера строк уже приводили к разъехавшейся справке. В этой сессии шаблон заменён в семи командах; осталось довести до одного вида и закрепить проверкой.

**Что делать.**

```sh
# help: печатает блок "# Usage:" из шапки вызвавшего скрипта (без номеров строк).
help() {

```

**Трудозатраты:** низкие. **Риск:** низкий. **Выигрыш:** правка комментариев больше не ломает интерфейс команд.

### II.7. Нормализовать переводы строк и перестать чинить их при деплое (находка 7)

**Зачем.** CRLF на Windows превращает файлы в «полностью изменённые» и ломает `sh -n` на роутере; сейчас спасает только `sed` внутри `deploy.ps1`.

**Что делать.**

1. Нормализовать рабочую копию (`git add --renormalize .`) и закоммитить — это уже сделано в текущей правке; `git status` перестаёт показывать файлы целиком изменёнными.
2. Оставить `sed` в `deploy.ps1`/`deploy.sh` как страховку, с комментарием, что это защита, а не механизм.
3. Добавить проверку перед коммитом: файл `kit/` не должен содержать CRLF.

```powershell
# tools/check-eol.ps1: CRLF в kit/ — ошибка
$bad = Get-ChildItem kit -Recurse -File | Where-Object { $_.Extension -ne '.gz' -and $_.Extension -ne '.png' } |
	Where-Object { [IO.File]::ReadAllBytes($_.FullName) -contains 13 }
if ($bad) { $bad | ForEach-Object { Write-Error "CRLF: $($_.FullName)" }; exit 1 }
```

**Проверка.** `git status` чист; запуск проверки на текущем дереве — успех. **Трудозатраты:** низкие. **Риск:** низкий (одноразовый коммит переводов строк). **Выигрыш:** исчезает целый класс «фантомных» изменений и падений разбора на роутере.

### II.8. Разделить `panel.cgi` (находка 8)

**Зачем.** 732 строки при договорённом пороге 600–700; каждая новая функция панели добавляет по 20–40 строк.

**Что делать.** Не «резать по строкам», а вынести по понятиям, подключая через `.`:

```
/www/flint/cgi-bin/
├── panel.cgi          # точка входа: язык, PIN, диспетчер действий, подключение частей
└── parts/
    ├── ui.sh          # top, langs, logo, btn, field, grid, card, esc, t
    ├── status.sh      # вкладка «Статус»
    ├── servers.sh     # «Серверы» и «Свои серверы»
    ├── subs.sh        # «Подписки»
    ├── dns.sh         # «DNS»
    ├── routing.sh     # «Маршрутизация»
    ├── adblock.sh     # «Реклама»
    ├── telegram.sh    # «Telegram»
    └── settings.sh    # «Настройки», PIN, экспорт/импорт
```

В `panel.cgi` остаётся:

```sh
. /www/flint/cgi-bin/parts/ui.sh
...
case "$tab" in
	status) . /www/flint/cgi-bin/parts/status.sh ;;
	servers) . /www/flint/cgi-bin/parts/servers.sh ;;
```

Установщик копирует каталог `parts` целиком и добавляет его в `keep.d` (там уже есть `/www/flint` — каталог переживёт прошивку, отдельная правка не нужна). Проверка `uhttpd` не даёт доступа к `parts/*.sh` снаружи: CGI-каталог уже ограничен (`-x /cgi-bin`), а файлы в подкаталоге не исполняются напрямую — но это надо проверить запросом `http://vpn.lan:81/cgi-bin/parts/ui.sh` (должен отдавать исходник или 403; если исходник — перенести части в `/usr/share/flint/panel/`).

**Проверка.** `tests/router/panel.sh` (126 проверок) без изменений должен пройти; плюс побайтовое сравнение HTML всех девяти вкладок до и после (как делали в этапе E плана 1.2).

**Трудозатраты:** средние–высокие. **Риск:** средний (разметка легко меняется — сравнение HTML обязательно). **Выигрыш:** панель снова в пределе, вкладки независимы, правка одной не рискует другими.

### II.9. Разгрузить `flint-sub-update` (наблюдение из ревью)

**Зачем.** 287 строк в одном файле: разбор base64, разбор ссылок, скачивание, построение конфигов, блокировки, cron, панель статусов.

**Что делать.** Вынести в `lib.sh` или в отдельный `/usr/share/flint/sub.sh` три чистые функции: `fetch` (скачать и превратить в TSV), `build` (собрать `nodes.d/*.conf`), `commit` (установить и переприменить). Ветки `case` станут короткими:

```sh
"") fetch_all || fail "..."; build; same || { last_check "..."; commit; } ;;
add) check_url "$2"; lock; id="$(next_id)"; fetch "$2" "$TMP/$id.tsv" || fail "..."; ... ;;
```

**Проверка.** `tests/run.ps1` (сценарии `subscription`, `failover`, `redeploy`) + сверка `nodes.d/*.conf` до и после (`md5sum`). **Трудозатраты:** средние. **Риск:** средний (подписки — ядро проекта; обязателен прогон всех трёх сценариев). **Выигрыш:** каждая часть тестируется отдельно, правки перестают задевать остальное.

### II.10. Возвращать АдГвард и dnscrypt после восстановления (находка 10)

**Зачем.** `/etc/flint-adguard` не входит ни в бэкап, ни в файл настроек; после восстановления данные фильтров скачиваются заново, и это выглядит как потеря настроек.

**Что делать.** Либо добавить `/etc/flint-adguard` в список путей бэкапа (`backup.ps1`/`backup.sh`), либо явно написать в README и в панели, что списки после восстановления перекачиваются, а `flint-adblock refresh` ускоряет это. Второй путь дешевле и честнее: файлы каталога — кеш загруженных списков, а не настройки.

**Проверка.** `restore` на тестовом роутере; в панели — что статистика и «Недавно заблокировано» появляются после `refresh`. **Трудозатраты:** низкие (документация) или средние (бэкап каталога). **Риск:** низкий.

## Группа III. Инструменты и процесс

### III.11. Починить обёртку тестов (находка 11)

**Зачем.** В этой сессии обёртка дважды зависла до дедлайна, а прогон на роутере при этом завершался сам.

**Что делать.** В [tests/run.ps1](../tests/run.ps1):

```powershell
# дедлайн — до цикла, чтобы он проверялся и при недоступном роутере
$deadline = (Get-Date).AddMinutes(30)
while ($true) {
	if ((Get-Date) -gt $deadline) { throw "No result after 30 minutes" }
	# все вызовы ssh — с теми же безопасными опциями, что и в $ssh
	$out = ssh @ssh $statusCmd 2>$null
	...
	if ($run -and $run.Status -eq "none") { throw "The run disappeared (router rebooted?): /tmp/flint-test.log is gone" }
	Start-Sleep 10
}
```

То же в [tests/run.sh](../tests/run.sh): добавить `-o BatchMode=yes -o ConnectTimeout=10` в опрос и проверку «лога нет — прогон исчез».

**Проверка.** Смоделировать недоступность: запустить прогон и на минуту выключить Wi-Fi роутера (или временно указать неверный адрес) — обёртка должна завершиться по дедлайну, а не висеть. **Трудозатраты:** низкие. **Риск:** низкий. **Выигрыш:** инструмент перестаёт требовать ручного вмешательства.

### III.12. Сделать проверки «панели» независимыми от исходного состояния (находка 12)

**Зачем.** Две упавшие проверки — про прокси Telegram и «занятый порт» — зависят от того, что было до теста.

**Что делать.** В [tests/router/panel.sh](../tests/router/panel.sh):

```sh
# Telegram: сравниваем с текущим состоянием, а не с ожидаемым «выключено»
if flint-tg state | grep -q '^on$'; then
	check "Telegram tab shows the off switch" panel_has telegram "name=tg value='off'"
else
	check "Telegram tab shows the on switch" panel_has telegram "name=tg value='on'"
fi
```

```sh
# «занятый порт»: берём любой чужой слушающий порт и ждём отказа — в любом из двух видов.
# Порт ниже 1024 отсекается проверкой диапазона раньше проверки занятости (на роутере это
# единственный кандидат — 443, его слушает Xray), поэтому принимаем оба сообщения.
busy="$(netstat -ltn | awk -v own="$(flint-tg port)" 'NR > 2 { sub(/.*:/, "", $4); if ($4 != own) print $4 }' | head -n1)"
if [ -n "$busy" ]; then
	panel "tab=telegram&tgport=$busy" >/tmp/flint-test-page
	check "a busy port is rejected" grep -qE 'уже занят|от 1024 до 65535' /tmp/flint-test-page
	check "a busy port does not change the setting" [ "$(flint-tg port)" != "$busy" ]
else
	echo "  skip  a busy port is rejected (no listening port found)"
fi
```

**Проверка.** Два прогона подряд: с включённым и с выключенным прокси — оба должны быть зелёными. **Трудозатраты:** низкие. **Риск:** низкий. **Выигрыш:** зелёный прогон снова означает «всё в порядке», а не «повезло с состоянием».

### III.13. Предкоммит-проверка секретов (обещана в плане 1.2, не сделана)

**Зачем.** В репозитории лежат только примеры настроек, а настоящие `config/flint.env`, `config/subscriptions`, `backup/` — в `.gitignore`. Ошибка в один `git add -f` уводит в публичный репозиторий ссылку подписки, UUID и пароль Wi-Fi.

**Что делать.** Скрипт `tools/check-secrets.ps1` (и `.sh`) + хук `.githooks/pre-commit`:

```powershell
# ищем в индексе то, чего там быть не должно
$bad = git grep --cached -n -E 'vless://|sdns://[A-Za-z0-9_-]{20,}|UI_PIN=[A-Za-z0-9]{4,}' -- ':!*.example' ':!docs/**' ':!LICENSE*'
if ($bad) { Write-Error "Похоже на секреты в индексе:`n$bad"; exit 1 }
```

Плюс включение хука: `git config core.hooksPath .githooks`. Токен подписки проверять отдельно: взять хост подписки из `config/subscriptions` (если файл есть) и искать его в индексе.

**Проверка.** Подложить в индекс строку `vless://test@example.com:443` — проверка должна отказать; убрать — пропустить. **Трудозатраты:** низкие. **Риск:** низкий. **Выигрыш:** публикация секрета становится почти невозможной.

### III.14. `CONTRIBUTING.md` и связка с README

Ссылку добавить в раздел «Участие в разработке» обоих README.

**Проверка.** Прочитать и пройти путь по шагам на чистой машине (или хотя бы сверить команды с фактическими). **Трудозатраты:** низкие. **Риск:** нет. **Выигрыш:** меньше вопросов в Issues, вклад приходит в принятом формате.

### III.15. `tests/demo.sh` для скриншотов и CI на синтаксис

**Зачем.** Скриншоты в README снимались вручную, а обещанный демо-скрипт так и не появился; при этом любая правка панели требует новых снимков.

### III.16. Отпечаток клиента и mux в шаблоне (по итогам I.3)

**Зачем.** Сейчас в [template.json](../kit/files/etc/xray/template.json) закреплён `fingerprint: firefox`, а по полевым наблюдениям Chrome/Safari/iOS чаще попадают под фильтр, Firefox и Android-клиенты проходят. Значение уже выбрано удачно, но не обосновано и не настраивается.

## Чего план не делает

- **Не меняет архитектуру**: `/etc/xray`, `/usr/share/flint/lib.sh`, CGI-панель на `uhttpd`, отсутствие Node/Python на роутере — остаются.
- **Не переписывает пары `.ps1`/`.sh`** у скриптов компьютера: логики там почти нет, дублирование приемлемо (зафиксировано в аудите 1.2).
- **Не переписывает историю git** и не переставляет опубликованные теги.
- **Не добавляет второй бинарник** (sing-box, AmneziaWG, Hysteria как отдельный демон): пока Xray 26.x закрывает то, что нужно, — см. исследование.
- **Не трогает YAML АдГварда**, собираемый `echo` в `flint-adblock`: простая и рабочая схема, шаблонизация — отдельная задача.
- **Не решает проблему «панель по HTTP с PIN в адресе»** переводом на HTTPS: это отдельный разговор про сертификаты на роутере; текущее ограничение честно описано в README.
