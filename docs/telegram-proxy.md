# Прокси для Telegram

MTProto-прокси на роутере — [tg-ws-proxy-rs](https://github.com/valnesfjord/tg-ws-proxy-rs), Rust-версия [Flowseal/tg-ws-proxy](https://github.com/Flowseal/tg-ws-proxy). Приложение Telegram подключается к роутеру как к обычному MTProto-прокси, а роутер ходит к Telegram через его веб-серверы по WebSocket поверх TLS — тем же путём, что и Telegram Web в браузере. Провайдер видит HTTPS-соединение с веб-сервером Telegram, а не протокол MTProto, который режут по сигнатуре.

## Зачем он нужен

При включённом VPN Telegram на устройствах за Flint и так работает: его серверы не российские, и гео-фильтр отправляет их через VLESS. Прокси нужен, когда Telegram должен работать **без VPN**:

- на **устройствах без VPN** («Маршрутизация → Устройства без VPN») — их трафик идёт мимо Xray, и Telegram у провайдера может тормозить или не работать;
- при **выключенном VPN** или когда серверы подписки недоступны — Telegram продолжит работать через прокси;
- **без расхода трафика подписки** — фото, видео и файлы идут мимо VLESS (путь «Напрямую»);
- **вне дома**, если открыть доступ из интернета: телефон в мобильной сети ходит в Telegram через домашний роутер.

Пока прокси выключен или не добавлен в Telegram на устройстве, Telegram идёт по обычным правилам роутера, как весь остальной трафик.

## Как включить

1. «Telegram → Включить прокси». Прокси уже на роутере (его ставит деплой), так что он стартует сразу; панель дождётся, пока он начнёт слушать порт.
2. Откройте вкладку «Telegram» на устройстве с Telegram и нажмите **«Добавить в Telegram»** — Telegram сам предложит подключить прокси. Кнопка `t.me` рядом — та же ссылка через сайт Telegram, на случай если приложение не открылось по `tg://`.
3. Вручную: *Настройки → Данные и память → Прокси → Добавить прокси → MTProto*; сервер, порт и секрет — с той же вкладки.

Ссылок до трёх, у каждой свой адрес сервера:

| Ссылка | Сервер | Для кого |
|---|---|---|
| В сети Flint | `192.168.8.1` (адрес LAN роутера) | устройства в Wi‑Fi или LAN Flint |
| В сети основного роутера | адрес Flint в сети основного роутера, например `192.168.0.111` | устройства в Wi‑Fi основного роутера; есть, если задан `UPSTREAM_NET` |
| Из интернета | IP провайдера или свой домен | телефон вне дома; есть, если включён доступ из интернета |

## Как это работает

```
 Telegram (телефон, ПК)
    │  MTProto, обфусцирован секретом (dd…), с маскировкой — в TLS-обёртке (ee…)
    ▼
 Flint :1443 ── tg-ws-proxy ─┬─► WebSocket по TLS :443 → kwsN.web.telegram.org ─► дата-центр Telegram
                             ├─► резерв: Cloudflare (kwsN.<домен из списка>)    ─► дата-центр Telegram
                             └─► последний вариант: TCP :443 прямо к дата-центру
    «Через VPN»: все исходящие соединения прокси идут в Xray (HTTP-вход 127.0.0.1:1087) ─► VLESS
```

1. **Подключение к роутеру.** Telegram открывает TCP-соединение с роутером на порт прокси (1443). Это адрес внутри сети, поэтому Xray его не трогает, даже если само устройство идёт через VPN.
2. **Рукопожатие и секрет.** Первые 64 байта — обфусцированное рукопожатие MTProto. Прокси проверяет по нему секрет и узнаёт номер дата-центра (DC) и тип соединения: обычное или медиа (фото, видео, файлы). Подключение без верного секрета отбрасывается — поэтому прокси нельзя использовать, просто зная адрес и порт.
3. **Мост в WebSocket.** Прокси открывает WebSocket-соединение `wss://kwsN.web.telegram.org/apiws` — вход Telegram Web для дата-центра N. TCP идёт на IP дата-центра, а в TLS указано имя веб-сервера, так что снаружи это выглядит как обычный HTTPS к Telegram Web. Поток перешифровывается AES-256-CTR (ключи клиента ↔ ключи моста). Содержимое переписки прокси не видит: его шифрует сам Telegram, и прокси передаёт уже зашифрованные данные.
4. **Пул соединений.** Для каждого дата-центра прокси держит 4 заранее открытых WebSocket-соединения, поэтому новые чаты и загрузки не ждут TLS-рукопожатия.
5. **Резервные пути.** Каждое соединение идёт первым путём, который сработал: прямой WebSocket → Cloudflare (если резерв включён) → прямое TCP-соединение с дата-центром на порт 443. Резерв через Cloudflare берёт общий список доменов проекта tg-ws-proxy: прокси скачивает его с GitHub при запуске, а если GitHub недоступен — берёт короткий встроенный список. За этими доменами стоят те же входы `kwsN`, но провайдер видит соединение с Cloudflare. Если TCP к адресу дата-центра повис по таймауту — так обычно выглядит блокировка через DPI, — прокси пропускает этот адрес на час и сразу идёт резервом. Отказ в соединении пропуском не считается. Если резервы тоже не работают, адрес пробуется снова, а первое удачное прямое подключение снимает пропуск.
6. **Путь к Telegram.** «Напрямую» — прокси выходит в интернет как сам роутер: собственный трафик роутера в Xray не заворачивается (перехват работает только для трафика из LAN), поэтому VPN не тратится. «Через VPN» — все исходящие соединения прокси, включая резерв через Cloudflare, идут в HTTP-вход Xray на `127.0.0.1:1087`, дальше по правилам Xray: адреса Telegram не российские, поэтому — через VLESS. Если VPN выключен или серверов нет, прокси сам переходит на «Напрямую» и возвращается обратно, когда VPN снова включат.
7. **Маскировка (FakeTLS).** С ней прокси принимает только клиентов с секретом `ee…`: соединение телефона с роутером начинается как TLS-рукопожатие с указанным сайтом (например, `www.google.com`). Это защищает участок «телефон → роутер», когда он идёт через интернет и мобильного оператора. Путь роутера к Telegram маскировка не меняет.

## Как устроено на роутере

| Что | Где |
|---|---|
| Прокси | `/usr/bin/tg-ws-proxy` — статический бинарник для aarch64 (3,8 МБ). Ставится при каждом деплое из архива `kit/bin/` |
| Служба | `/etc/init.d/flint-tgproxy` (procd, перезапуск при падении). Включена в автозапуск, только пока прокси включён в панели |
| Настройки | `/etc/xray/tgproxy`, права 600: `state`, `route`, `cf`, `remote`, `addr`, `mask`, `port`, `secret`, `dc`, `cfdomain`, `worker`, `cftls`, `pool`, `log` |
| Управление | `flint-tg` — им пользуются панель, `install.sh` и `firewall.user` |
| Firewall | из сети Flint вход на роутер открыт зоной `lan`; из сети основного роутера — правилом `Allow-Upstream-LAN-to-Router`; из интернета — правилом `Allow-Flint-Telegram-Proxy` (`firewall.flint_tg_remote`), которое существует, только пока включён доступ из интернета, и следует за сменой порта |

Подробности:

- **Параметры запуска** собирает `flint-tg args`: `--host 0.0.0.0 --port <порт> --link-ip <адрес LAN>`, плюс `--default-domains` (резерв через Cloudflare), `--listen-faketls-domain <сайт>` (маскировка) и `--outbound-proxy http://127.0.0.1:1087` (путь через VPN, пока VPN работает). Секрет передаётся в переменной окружения `TG_SECRET`, поэтому в списке процессов (`ps`) его не видно.
- **Синхронизация.** `flint-tg sync` вызывается в конце `/etc/firewall.user`, то есть при включении и выключении VPN, смене сервера, перезагрузке firewall и загрузке роутера. Он перезапускает прокси, только если изменились параметры запуска или секрет (последние запомнены в `/tmp/flint-tg.applied`), поэтому открытые соединения Telegram зря не рвутся.
- **Секрет** — 16 случайных байт (32 hex-символа), создаётся при первом обращении. Ссылка: `tg://proxy?server=<адрес>&port=<порт>&secret=dd<секрет>`, с маскировкой — `secret=ee<секрет><домен сайта в hex>`.
- **Проверка** («Проверить прокси», `flint-tg check`) запускает вторую копию прокси с теми же настройками на соседнем порту (`порт + 1`, только `127.0.0.1`) с ключом `--check-listener`. Эта копия сама подключается к себе как клиент Telegram — рукопожатие, запрос `req_pq_multi`, ответ `resPQ` от дата-центра, — проверяет домены Cloudflare и выдаёт строки `[OK]` / `[FAIL]` по каждому пути. Работающий прокси при этом не трогается.

## Откуда берётся прокси

Чтобы не зависеть от того, жив ли проект на GitHub, архив релиза хранится в репозитории: `kit/bin/tg-ws-proxy-aarch64-unknown-linux-musl.tar.gz` (v2.5.2) и лицензия MIT `kit/bin/tg-ws-proxy-LICENSE`. Деплой заливает его вместе с комплектом, `install.sh` проверяет SHA-256 архива по сумме из `flint-tg` и ставит `/usr/bin/tg-ws-proxy`. Если архив в комплекте отсутствует или повреждён, установка продолжается без прокси, а `flint-tg on` (кнопка в панели) скачает тот же архив с GitHub — сначала через VPN, потом напрямую — и проверит ту же сумму. Чужой или изменённый файл не установится.

**Обновить прокси до новой версии:**

1. Скачайте `tg-ws-proxy-aarch64-unknown-linux-musl.tar.gz` из [релизов tg-ws-proxy-rs](https://github.com/valnesfjord/tg-ws-proxy-rs/releases) и замените им архив в `kit/bin/`.
2. В `kit/files/usr/bin/flint-tg` поменяйте `VERSION` и `SHA256` (сумма архива: `Get-FileHash <файл> -Algorithm SHA256` или `sha256sum <файл>`; GitHub показывает её у файла в релизе).
3. Повторите деплой. Прокси перезапустится на новой версии с прежними настройками и секретом — ссылки в Telegram менять не нужно.

## Что через прокси не идёт

- **Звонки Telegram.** MTProto-прокси их не передаёт. Звонки идут по обычным правилам сети: UDP за Flint не туннелируется и идёт напрямую.
- **Telegram Web в браузере.** Это обычный сайт: он идёт по правилам роутера — через VPN, если тот включён.
- **Устройства, на которых прокси не добавлен в Telegram.** Прозрачно, без настройки в приложении, прокси не работает.

## Переключатели

| Настройка | Что делает |
|---|---|
| Путь к Telegram | **напрямую, мимо VPN** (по умолчанию) или **через VPN** — если провайдер мешает и веб-серверам Telegram. Пока VPN выключен, прокси в любом случае ходит напрямую |
| Резерв через Cloudflare | если серверы Telegram недоступны, прокси идёт к ним через Cloudflare по общему списку доменов проекта tg-ws-proxy (включён по умолчанию) |
| Доступ из интернета | открывает порт прокси в зоне WAN, чтобы Telegram на телефоне работал через домашний роутер и вне дома. Нужен проброс TCP-порта на основном роутере на адрес Flint в его сети и «белый» IP у провайдера (за CGNAT не заработает). Адрес в ссылке — IP провайдера или свой домен (DDNS) |
| Порт | 1443 по умолчанию |
| Маскировка (FakeTLS) | соединение с прокси выглядит как HTTPS к указанному сайту (ссылка с секретом `ee…`). Включайте, когда прокси открыт из интернета: без неё мобильный оператор может распознать прокси |
| Новый секрет | старые ссылки перестают работать |
| Свой секрет | 32 hex-символа, например из десктопного tg-ws-proxy, чтобы не менять секрет в Telegram (подойдёт и секрет с `dd`/`ee` в начале) |
| Адреса дата-центров | номер:IP через запятую (`--dc-ip`), к каким адресам прокси подключается напрямую. Пусто — встроенные адреса (DC2 и DC4) |
| Cloudflare: свои домены | домены на вашем Cloudflare (`--cf-domain`), пробуются раньше общего списка |
| Cloudflare Worker | домены вашего Worker (`--cf-worker-domain`) — последний резерв, TCP-туннель до Telegram |
| TLS к Cloudflare | выключение — `ws://` на порт 80 (`--cf-disable-tls`), только если провайдер режет TLS к Cloudflare |
| Пул WebSocket-соединений | сколько соединений с каждым дата-центром держать открытыми заранее (`--pool-size`, по умолчанию 4) |
| Журнал прокси | выключен, включён или подробный (`--verbose`); пишется в системный журнал роутера в памяти (`logread -e tg-ws-proxy`), последние строки видны на вкладке |
| Проверить обновления | сравнивает установленную версию с последней на GitHub. Сама не обновляет: версия закреплена в комплекте, см. [Откуда берётся прокси](#откуда-берётся-прокси) |

Параметр «Буфер, КБ» из десктопного tg-ws-proxy не перенесён: Rust-версия его принимает, но не использует.

После смены порта, маскировки или секрета добавьте прокси в Telegram заново. «Проверить прокси» запускает вторую копию прокси с теми же настройками и проходит путь целиком — от подключения клиента до ответа серверов Telegram — и показывает результат по каждому пути (`[OK]` / `[FAIL]`).

## Ресурсы, бэкап, прошивка

- Прокси занимает 3–5 МБ памяти и 3,8 МБ на флеше; при выключении он остановлен.
- Настройки и секрет (`/etc/xray/tgproxy`) попадают в бэкап, файл настроек панели и восстанавливаются `restore` — ссылки в Telegram после восстановления остаются рабочими.
- Обновление прошивки с «Сохранить настройки» сохраняет прокси вместе с остальным комплектом (см. [Обслуживание](maintenance.md#обновление-прошивки)). Без неё прокси поставит повторный деплой из `kit/bin/`, интернет для этого не нужен.
- `uninstall` останавливает прокси, удаляет бинарник, службу и правило firewall.
