Почему версии такие:

- **Этап A** исправляет ошибку и удаляет `sub2nodes.py`. Это инструмент компьютера, а не роутера, поэтому достаточно патч-версии.
- **Этап B** меняет только скрипты компьютера и тесты. Формат бэкапа остаётся совместимым (см. ниже).

- **Этапы E и F** — внутренние упрощения без видимых изменений.

### Общие правила для каждого этапа

1. **Один этап — один коммит или несколько.** На каждую версию свой тег `vX.Y.Z`; несколько тегов на одном коммите больше не ставить (находка 11).
2. **До коммита:**
   - деплой на роутер;
   - прогон `tests/run.ps1` (все сценарии, включая новые проверки этапа);
   - ручная проверка панели на вкладках, которых касался этап.
3. **Документы:** запись в `CHANGELOG.md` и `CHANGELOG.en.md`, номер в `kit/VERSION`. Если меняются команды или файлы — правка README на обоих языках.
4. **Проверка секретов перед коммитом:**
   - выполнить `"C:\Program Files\Git\bin\bash.exe" "$env:TEMP/flint-precommit.sh"`;
   - убедиться, что `git grep --cached` по токену подписки и по имени её хоста ничего не находит.

   В git не попадают ссылки VLESS и подписок, пароль root, `/etc/xray/config.json`, файлы `config/` (кроме `*.example`), `backup/` и `tmp/`.
5. **Перед этапами B и C** сделать бэкап роутера (`backup.ps1 -WithBinary`): они трогают бэкап, восстановление и установку.
6. **Откат этапа:** `git revert` коммита этапа и повторный деплой. Если деплой сломан — `restore.ps1` из последнего бэкапа.

### Идея

Ввести понятие «пользовательское состояние роутера». Это файлы и каталоги в `/etc/xray`, которые создаёт пользователь (через `flint.env` или панель) и которые нужно переносить при бэкапе, восстановлении и деплое. Описывается оно **одним списком в одном файле**. Скрипты обрабатывают каждый элемент одинаково, как файл или каталог, и не знают имён.

1. **Создать `kit/state-files`** — по одному имени в строке, с комментарием в шапке:

   ```
   nodes.conf
   nodes-custom.conf
   nodes.d
   custom-sites
   subscriptions
   adblock-lists
   adblock-rules
   adblock-exclude
   ```

3. **`backup.ps1` / `backup.sh`.** Заменить цикл по файлам (по одному `ssh` на файл, сейчас до 9 подключений) и отдельный блок `nodes.d` одним архивом:

## Этап D. Правило для `set -e` (находка 7) — 1.3.0

### Решение

`set -e` остаётся **только в `kit/install.sh`**: это линейная установка, где любая ошибка должна её остановить. Команды роутера (`flint-*`) работают без `set -e` и проверяют ошибки явно. Так уже устроены `flint-sub-update`, `flint-adblock` и `flint-watchdog`: у них есть `fail()` и `|| exit 1` на важных шагах.

### Шаги

1. **`flint-node`** — убрать `set -e`. Явные проверки нужны в таких местах:
   - `apply`: проверка неизвестного кода и ошибки `render` уже обрабатываются явно;
   - `mv "$CONF.new" "$CONF"` → `|| fail "Cannot write $CONF"`;
   - запись `current-node`, `routing-mode`, `vpn-state`, `custom-sites` → `|| fail …`;
   - `site add|del`: запись `custom-sites.new` и `mv` → `|| fail …`;
   - добавить `fail() { echo "$1"; exit 1; }` рядом с остальными помощниками.
2. **`flint-custom`** — убрать `set -e`. Проверить так же: `mv "$CUSTOM.new" "$CUSTOM"` в `set_node` и `del` → `|| fail`; `fail` объявить по образцу.
3. **`install.sh`** — оставить `set -e`. Просмотреть все `[ … ] && …`: если такая конструкция стоит последней в функции или блоке, переписать на `if`.
4. **Записать правило** в комментарий шапки `lib.sh` (или в раздел README для разработчиков): «Команды flint-* не используют set -e: ошибки проверяются явно через fail. set -e — только в install.sh».
5. **Найти оставшиеся опасные места** до и после:

   ```sh
   grep -n '^\s*\[.*\] && [^|]*$' kit/install.sh
   ```

## Этап E. Разгрузка `panel.cgi` (находка 8) — 1.3.1

### Шаги

2. **Передавать действие один раз.** Сравнивались два варианта:

   - **Вариант 1 (рекомендуется).** `a` вычисляется по первому найденному параметру из упорядоченного списка действий, а скрытые поля `name=a` удаляются из всех 23 форм:

     ```sh
     ACTIONS="node routing vpn sub subint subadd subsave subdel wd adblock abpreset ablist abldel abrule abrdel abint abref abxadd abxdel add del link ndel save edit copy newnode"
     a=""; for x in $ACTIONS; do [ -n "$(raw "$x")" ] && { a="$x"; break; }; done
     ```

     Порядок важен там, где форма отправляет несколько полей-действий. Например, `save` вместе с `n`, `h` и `p` — это не действия, конфликта нет. Порядок нужно проверить по каждой форме и записать в комментарии над списком.

3. **Читать параметры лениво.** Глобальное чтение около 35 параметров (строки 38–46) заменить чтением внутри веток `case`. Например:

