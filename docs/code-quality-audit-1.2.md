# Аудит качества кода — версия 1.2.0

Второй строгий аудит поддерживаемости Flint VPN, теперь всего проекта целиком, после выполнения [первого плана](refactoring-plan.md). Оцениваются структура, дублирование, границы модулей и размер файлов. Попутно найдена одна поведенческая ошибка: она описана первой.

- План исправлений по этому аудиту — [refactoring-plan-1.2.md](refactoring-plan-1.2.md).
- Предыдущий аудит (версия 1.1.0) — [code-quality-audit.md](code-quality-audit.md).

## Итог

**Как PR это не прошло бы ревью.** С размером файлов всё в порядке. Основные проблемы такие:

- **Одна ошибка поведения.** Это находка 1: `sub2nodes.py` и заливка `nodes.conf` не учитывают модель 1.2.0.
- **Повторы знания о данных.** Список файлов настроек, раскладка файлов серверов и разбор их строк повторены в 5–7 местах. Из-за этого этап 5 первого плана пришлось вносить в шесть файлов, хотя по смыслу хватило бы одного.

Первый план сократил дублирование выбора сервера и признака «серверов нет». Но перенос серверов в `nodes.d/` добавил новый круг таких же повторов, и в плане он не рассматривался.

**Сильные стороны:**

- Модули разделены здраво: подписки — `flint-sub-update`, выбор сервера — `flint-node`, свои серверы — `flint-custom`, а панель только вызывает команды.
- Выбором сервера теперь владеет одна команда (`flint-node apply`).
- Есть сценарии на роутере (`tests/router/`, 47 проверок), с которыми рефакторинг больше не идёт вслепую.

## Находки

Находки упорядочены по важности: сначала ошибка поведения, затем структурные повторы, потом локальные упрощения.

### 1. `tools/sub2nodes.py` и заливка `nodes.conf` не учитывают модель 1.2.0 (ошибка)

**Что не так.** С 1.2.0 `nodes.conf` означает «серверы, заданные вручную», а серверы подписки лежат в `nodes.d/<id>.conf`. Два места продолжают работать по старой схеме.

Первое — `tools/sub2nodes.py` (строки 21 и 103). Он записывает **серверы подписки** в `config/nodes.conf`, и README советует этот шаг при первой установке.

Второе — условие заливки в `kit/install.sh` (строка 114):

```sh
if [ -f "$KIT/config/nodes.conf" ] && { [ ! -s /etc/xray/nodes.conf ] || [ ! -s /etc/xray/subscriptions ]; }; then
```

После переноса `/etc/xray/nodes.conf` на роутере пустой (проверено на роутере: размер 0). Значит, условие `! -s` истинно всегда, и копия с компьютера перезаписывает файл на роутере **при каждом деплое**. Комментарий над условием утверждает обратное.

**Последствия:**

- **Дубли серверов.** Кто выполнит `sub2nodes.py` по README, получит одни и те же серверы дважды. Одна копия окажется в «ручных» и никогда не обновится, другая — в `nodes.d/s1.conf`. В панели появятся две карточки с одинаковым заголовком «Серверы».
- **Откат к устаревшему списку.** Если в `config/nodes.conf` лежит копия из бэкапа версии до 1.2 (с разметкой `#@`), деплой снова запустит перенос. Он затрёт свежий `nodes.d/s1.conf` старыми данными, и они будут жить до следующего обновления подписки.

**Как исправить.** Удалить `sub2nodes.py`: роутер сам строит список из `SUB_URL` при установке и по расписанию. После этого `config/nodes.conf` становится обычным файлом настроек, как `custom-sites`: если он есть, деплой его заливает. Перенос `#@` не должен перезаписывать уже существующие `nodes.d/<id>.conf`.

**Статус:** исправлено в 1.2.1, этап A плана.

### 2. Список файлов настроек повторён семь раз

**Что не так.** Строка `flint.env nodes.conf nodes-custom.conf custom-sites subscriptions adblock-lists adblock-rules adblock-exclude` скопирована в семь мест:

| Файл | Строки |
|---|---|
| `deploy.ps1` | 21 |
| `deploy.sh` | 19 |
| `backup.ps1` | 22 |
| `backup.sh` | 21 |
| `restore.ps1` | 28 |
| `restore.sh` | 39 и 59 |
| `kit/install.sh` | 119, частично |

В 1.2.0 в каждый из этих файлов отдельно дописывали обработку каталога `nodes.d`:

- `deploy.ps1` 25–26, `deploy.sh` 22;
- `backup.ps1` 30–39, `backup.sh` 28–33;
- `restore.ps1` 40–63, `restore.sh` 43–70;
- `install.sh` 114–117.

Это главный признак того, что модели не хватает понятия «пользовательское состояние». Сейчас его заменяют семь копий списка.

**Почему это важно.** Каждый новый файл настроек нужно добавить в семь мест на двух языках. Если пропустить одно, бэкап молча перестанет сохранять настройку или деплой перестанет её заливать. Тесты такое не ловят: сценарии работают на роутере и скрипты компьютера не проверяют.

**Как исправить.** Нужен один список в репозитории, например `kit/state-files`, по одному имени в строке, вместе с `nodes.d`. Его читают все скрипты компьютера, а `install.sh` получает его вместе с комплектом. Скрипты обрабатывают элементы единообразно, как файл или каталог: PowerShell `Copy-Item -Recurse`, sh `cp -R`. Особое правило остаётся только одно — в `install.sh`: `nodes.d` с компьютера лишь наполняет роутер, у которого своих серверов подписок ещё нет. Подробности — в этапе B плана.

**Статус:** исправлено в 1.2.2, этап B плана (проверка восстановления из бэкапа отложена).

### 3. Раскладка файлов серверов и разбор их строк описаны в пяти местах

**Что не так.** Список файлов серверов (`nodes.conf`, `nodes.d/*.conf`, `nodes-custom.conf`) собирался в пяти местах:

- `flint-node` → `node_files()`;
- `flint-custom` → своя копия `all_node_files()`;
- `etc/firewall.user` (строка 28) → пути прямо в коде;
- `flint-sub-update` → `seed_used()` и `install_one()`;
- `tests/router/lib.sh` → ещё одна `node_files()`.

Разбор формата «комментарий над строкой — название сервера» тоже был сделан дважды, каждый раз со своим awk: `flint-node names` и `flint-custom entries`. Подстановки по умолчанию (UUID из `VLESS_UUID`, порт 443, транспорт `tcp`) были реализованы в трёх местах: в двух этих awk и в `flint-node render`.

Константы путей `NODES`, `NODES_D`, `CUSTOM`, `CUR`, `SUBS` повторялись в каждом скрипте. Файл `current-node` читался напрямую в `flint-watchdog` (строка 43), в `flint-custom` (строки 15, 48, 98) и в тестах. Это было в обход команды `flint-node current`, которую первый план завёл именно для того, чтобы скрыть этот признак.

**Попутная ошибка.** В `flint-custom del` последняя команда сценария имела вид `[ ... ] && flint-node apply`. При `set -e` команда завершалась с кодом 1 всякий раз, когда удалялся не текущий сервер.

**Как исправить.** Перенести в `lib.sh` константы путей, `node_files` и одну функцию разбора `nodes_tsv`. Она выдаёт `код название адрес порт uuid sni pbk sid транспорт сервис группа` с уже подставленными значениями по умолчанию. Остальные скрипты становятся её потребителями, а `current-node` читает только `flint-node`.

**Статус:** исправлено в 1.2.1, этап A плана.

### 4. Два источника правды: `subscriptions` и содержимое `nodes.d/`

**Что не так.** `node_files` брал все файлы `nodes.d/*.conf`, а панель группирует серверы по списку `subscriptions`. Файл `nodes.d/<id>.conf` без строки в `subscriptions` продолжал работать:

- его серверы участвовали в выборе и в правилах firewall;
- в панели они не отображались, и удалить их оттуда было нельзя.

Получить такое состояние легко. При восстановлении `subscriptions` заливается всегда, а `nodes.d` — только если на роутере каталог пуст.

**Как исправить.** Считать `subscriptions` единственным списком. `node_files` читает только `nodes.d/<id>.conf` для id из списка, а `flint-sub-update` удаляет лишние файлы при каждой записи и при удалении подписки.

**Статус:** исправлено в 1.2.1, этап A плана. В сценарий `subscription` добавлены две проверки.

### 5. `flint-sub-update`: `install_one` дублирует `build` и `commit`

**Что не так.** Функция `install_one` (строки 120–139) повторяла `seed_used`, `build` и `commit` с минимальными отличиями. Её вызывали ветки `add` и `set`. Кроме того, ветка обновления всех подписок пересчитывала число серверов отдельным циклом (строки 299–304), хотя `build` и так проходит по всем подпискам.

**Как исправить.** Удалить `install_one`: ветки `add` и `set` вызывают `build; commit`. Поручить `build` заодно считать итоговое число серверов (`total`).

**Статус:** исправлено в 1.2.1, этап A плана.

### 6. `install.sh` — один линейный сценарий, в котором смешано всё

**Что не так.** В 259 строках подряд идут:

- установка пакетов;
- очистка следов старого комплекта `gru-*` (строки 62–85);
- перенос `#@` в `nodes.d/` (строки 122–150);
- заливка настроек;
- настройка dnsmasq;
- около 40 строк `uci set` для правил firewall (строки 168–216);
- запуск сервисов и итоговые проверки.

Миграции со старых версий занимают около 50 строк, и срок их удаления нигде не обозначен.

Правила доступа из сети основного роутера дословно продублированы в `kit/upstream-access.sh`. Там к тому же жёстко прописаны интерфейс `sta1` и сеть `192.168.0.0/24` вместо `UPSTREAM_IF` и `UPSTREAM_NET` из `flint.env`. Если правила поменять в одном месте, они разойдутся.

**Как исправить:**

- вынести миграции в `kit/migrate.sh` с комментарием, начиная с какой версии их можно удалить;
- заменить цепочки `uci set` одним `uci batch` с heredoc;
- удалить `upstream-access.sh`: повторный деплой делает то же самое по настройкам из `flint.env`.

Подробности — в этапе C плана.

**Статус:** исправлено в 1.3.0, этап C плана.

### 7. Нет единого правила для `set -e`

**Что не так.** `set -e` включён в `install.sh`, `flint-node`, `flint-custom` и `upstream-access.sh`, а в остальных скриптах его нет. Из-за привычных для shell конструкций это уже дало три настоящих сбоя:

- `[ -s "$CONF" ] && had=1` в `flint-node`;
- `cat` отсутствующего `current-node` внутри `pick()`;
- `[ ... ] && flint-node apply` в конце `flint-custom del` (см. находку 3).

Читатель скрипта не может понять, оборвёт ли выполнение очередная неудачная проверка.

**Как исправить.** Принять одно правило и записать его. Рекомендуется так: `set -e` остаётся только в `install.sh`, где нужна быстрая остановка линейной установки. Команды роутера (`flint-*`), которые вызывают панель и cron, проверяют ошибки явно через `fail`/`|| exit 1` на нужных шагах. Подробности — в этапе D плана.

**Статус:** исправлено в 1.3.0, этап D плана.

### 8. `panel.cgi`: хак со ссылкой на `flint.env` и избыточная передача действий

**Что не так:**

- **Хак ради панели.** `install.sh` (строка 98) создаёт ссылку `/usr/share/flint/env → /etc/xray/flint.env` только ради того, чтобы в `panel.cgi` (строка 18) не было пути `/etc/xray`. Это лишняя движущаяся часть: путь прячется, а зависимость остаётся.
- **Имя действия передаётся дважды.** Каждая форма отправляет и `a=X`, и параметр `X=…`. В панели 23 скрытых поля `name=a`, и каждое повторяет имя соседнего поля.
- **Параметры разбираются заранее.** Около 35 параметров разбираются глобально, ещё до диспетчера (строки 38–46), хотя каждой ветке нужны два-три из них.
- **Мелочи.** Ветки `"") ;;` и `*) ;;` в конце `case "$a"` ничего не делают. Подстановка `CUR="${CUR:-unknown}"` (строка 140) прячет пустое значение вместо того, чтобы панель явно показывала режим без серверов.

**Как исправить.** Подключать `/etc/xray/flint.env` напрямую и удалить ссылку. Вычислять `a` по первому найденному параметру из упорядоченного списка действий и удалить скрытые поля `name=a`. Читать параметры внутри веток `case`. Подробности и варианты — в этапе E плана.

**Статус:** не исправлено.

### 9. `flint-adblock` разбирает JSON регулярными выражениями

**Что не так.** Ответы API AdGuard Home разбираются через `tr` и `sed`, и правильный результат зависит от порядка ключей в JSON:

- строки 165–166 — `/filtering/status`;
- строки 276–277 — `/stats`.

Любое обновление AdGuard Home, которое поменяет порядок ключей, молча сломает статистику и даты обновления списков. Ошибки при этом не будет, будут пустые значения.

**Как исправить.** В OpenWrt есть штатный `jsonfilter`: он входит в стандартные образы, а его наличие на этом роутере проверяется первым шагом этапа F. Нужно заменить `sed` на выражения вида `jsonfilter -e '@.filters[*].url'`. Подробности — в этапе F плана.

**Статус:** не исправлено.

### 10. `tests/run.ps1` повторяет загрузку комплекта из `deploy.ps1`, а сценарии проверяют установленный код

**Что не так:**

- **Повтор логики.** `tests/run.ps1` (строки 15–29) и `tests/run.sh` повторяют упаковку и загрузку из `deploy.ps1` и `deploy.sh`.
- **Проверяется не тот код.** Сценарий `empty` переустанавливает комплект из рабочей копии, а остальные сценарии работают с тем, что уже стоит на роутере. Если `empty` не запускать, проверяется **установленная** версия, а не изменения в рабочей копии.

**Как исправить.** Пусть `tests/run.*` сначала вызывает `deploy.*`, затем заливает только `tests/router/` и запускает `all.sh`. Повтор исчезает, и сценарии всегда проверяют текущий код. Подробности — в этапе B плана.

**Статус:** исправлено в 1.2.2, этап B плана.

### 11. Процесс: три тега на одном коммите

**Что не так.** Теги `v1.1.1`, `v1.1.2` и `v1.2.0` стоят на одном коммите `f424de9`, поэтому отдельно установить 1.1.1 или 1.1.2 нельзя. Кроме того, перенос `#@` проверялся только на настоящем роутере с одной подпиской. Сценариев с двумя подписками, со строками без разметки и с восстановлением бэкапа 1.1.x нет.

**Как исправить.** Историю не переписывать: теги уже опубликованы. Дальше на каждый этап — отдельный коммит и отдельный тег. Сценарий повторного деплоя со старым `config/nodes.conf` добавляется в этапе A.

**Статус:** правило процесса, применяется к следующим этапам.

## Что не стали считать проблемой

- **Пары `.ps1` и `.sh` у скриптов компьютера.** Пользователи Windows работают из PowerShell, а Git Bash там не всегда есть и легко путается с `bash` из WSL. После этапа B в этих скриптах почти не останется логики, поэтому дублирование станет приемлемым.
- **Размер `panel.cgi`.** 418 строк — нормально для CGI-страницы с шестью вкладками. Делить её на файлы стоит, только если она перерастёт 600–700 строк.
- **`vless.awk` на роутере.** После удаления `sub2nodes.py` это единственный разборщик ссылок, «двойника» больше нет.

## Как оценивались находки

Применялись правила строгого аудита (`thermo-nuclear-code-quality-review`):

- искать перестройки, после которых целые ветки, функции или копии исчезают, а не переставляются;
- не допускать роста файлов за 1000 строк;
- не допускать особых случаев, разбросанных по общим путям;
- держать логику в слое, который владеет понятием.

Мелкие замечания по стилю в отчёт не включались.
